# SKR-019 — Typed contracts and frontend generation

## Frontend implementation

The actual API OpenAPI is exported by `scripts/export_contracts.py` into
`apps/web/contracts/openapi.json`. `openapi-typescript` **7.10.1** generates
`apps/web/src/generated/api.ts`; core DTO and source aliases in the API client
reference those generated components. No copied handwritten backend DTO is used.
The existing composer request and accepted-job display types remain local UI
state, not claims that unimplemented conversation endpoints exist.

The generator is a separate pinned pnpm workspace with TypeScript **5.9.3**, whose
AST API the generator requires. The app retains TypeScript **7.0.2**. Frozen
installation passed after completing the local store with an approved online
install. Docker's dependency layer copies both workspace/package manifests;
no Docker build was performed for this ticket.

Backend CI checks the committed OpenAPI against the actual API. Frontend CI
checks committed types against that OpenAPI before test/build/typecheck.
Generation/check commands and update instructions are in `apps/web/README.md`.

Actual SKR-026 snapshot/events routes and JobSnapshot/ProgressEvent schemas were
included in the final export. The client adds workspace-scoped snapshot and
stream transports with generated identity/payload types. Bearer and replay
cursor values travel only in headers; IDs are encoded in paths. The SSE decoder
handles fragmented CRLF frames and heartbeats, preserves large replay IDs as
strings, validates progress envelopes, bounds frame memory and releases readers
when cancelled or a consumer exits. It does not render progress or implement
automatic reconnect, so this does not close later frontend UX tickets.
