# SKR-055 — immutable saved-list snapshot and refresh component

Implemented `skriller.lists` and migration 0016 (saved_lists/list_snapshots). A list references a tenant-owned persisted immutable plan; its interpretation, workspace, conversation and revision are validated before use. Only owners create/refresh lists; workspace members can read snapshots. Forced RLS and immutable-table triggers preserve the historical records. Refresh uses a scoped advisory transaction lock and an expected latest revision to avoid lost updates.

Each snapshot freezes membership, qualification outcome, scalar values and evidence identity/source/excerpt/collection time. Role freshness comes from the original entity's explicit dated role history through the qualification adapter. New accepted role facts produce a new revision, while the old snapshot remains byte-equivalent and inspectable. Contact values require original-person published professional evidence; approved identity grouping cannot transfer another record's email ownership. Evidence excerpts are capped at 4096 characters and explicitly labelled when truncated.

Current bounds: 100 unique requested entities, 30 facts per entity, 100 suppressions and 1 MiB total serialized snapshot payload. Exceeding a bound fails without replacing a previous snapshot. Refresh is limited to persisted reviewed facts; it makes no external provider calls and is not a background fetch scheduler.

Suppression applies on every refresh. A suppressed entity cannot reappear through an approved identity-group alias or an exact accepted platform-native identity under a changed URL. Profile suppressions compare canonical URLs and verified native identity, preserving original records rather than merging them. Matching unverified native identity is explicitly `suppression_unresolved`, retains a near-match/review-required outcome, and exposes no values; it is neither automatically merged nor promoted. Person/company domain and name similarity cannot establish person identity. Snapshot history is not rewritten when a later suppression is added.

Verification: **39 tests passed** across seven new PostgreSQL saved-list checks and 32 contact/identity regressions. Ruff and MyPy pass. Tests cover role changes with old snapshot/evidence preserved, immutable history, reviewed aliases at another URL, profile suppression through a verified native identity without merging, unverified identity retained as unknown, professional contact ownership, refresh bounds, owner/member rights, foreign tenant plans/snapshots and stale revision rejection.

Production gates remain: authenticated list API/UI, durable external refresh scheduling, complete suppression/privacy request administration and privacy erasure/retention handling for historical snapshots/exports. This component does not claim those tickets finished or a live-source refresh test passed.

## Authenticated API follow-up — 2026-10-13

Added the typed authenticated `/v1/workspaces/{workspace_id}/lists` router: owner create, owner refresh with a strict integer expected revision, member enumeration/latest/historical reads, and owner entity/profile/email/domain suppression creation. Inputs accept persisted plan/entity IDs only and reject caller-supplied lead values. Outputs expose typed snapshot membership, qualification, evidence and omission records; the suppression response explicitly states that it applies to future refreshes and leaves historical snapshots unchanged. Snapshot responses include revision/view headers, revision ETags and `private, no-store`. Stale revision refresh returns structured HTTP 409; foreign resources or unavailable workspaces return 404, while a workspace member attempting an owner mutation receives 403. Suppression keys are canonicalized and repeat creation is idempotent.

## Saved-list UI closure — 2026-10-14

Added a workspace saved-list experience to the research results view. Members can load lists and inspect immutable revisions, frozen facts, evidence links, and suppressed omissions. Owners can select up to 100 current result IDs, create a named list (which creates revision 1 through the existing API), and explicitly create a new revision using the displayed expected revision. Stale revision and owner-only failures remain visible. The interface states that refresh evaluates persisted reviewed facts and does not fetch source pages. Historical revisions remain selectable without replacing the current revision.
