strict duplicate-key/invalid JSON rejection, Stripe timestamp tolerance and

authority.

## 2026-10-17 — access enforcement and authoritative reconciliation

Migrations 0037/0038 add operator-owned subscription bindings and a durable
reconciliation audit. One billing authority per workspace prevents stacking
Stripe/Razorpay allowances. New bindings start disabled. Tenant application
credentials cannot bind a subscription or mutate provider access/audit records.
The scoped security-definer read function returns only an access boolean.

Both normal policy reads and an independent database admission trigger enforce
paid access and expiry. Owner enabled/pause settings remain separate: setting
enabled=true cannot bypass a canceled or expired billing binding. Existing
trial/manual-pilot workspaces without billing bindings retain their finite
policies. Archived billing access is disabled on actual backup restore.

Reconciliation locks the workspace/policy before retrieving current provider
state. It validates subscription/account/customer/plan against explicit
operator-owned binding/catalog inputs, then atomically updates a short access
lease, bounded pilot ceilings, audit and event state. Old webhook snapshots
never grant access; duplicate reconciled events do not fetch or grant twice.
Caps remain finite lifetime pilot ceilings, not recurring-credit promises.
Existing admissions, owner pause and lower per-run settings are preserved.
Provider read failures/mismatched identities roll back. Leases expire within
15 minutes or the paid period end; an absent refresh worker fails closed.

Read-only clients use fixed Stripe/Razorpay HTTPS GET endpoints, explicit key
mode, bounded body/deadline/timeouts, no redirects/proxies/retries and generic
errors. Stripe version must be explicitly configured; the reviewed parser
requires subscription-item period fields and an expanded paid invoice tied to
the same customer/subscription. Active status alone, paused collection and an
unexpanded/open invoice do not grant paid access. Razorpay requires a paid
cycle and valid period, matching the documented subscription contract.

Verified real PostgreSQL tests cover owner enable bypass, direct SQL admission
denial, expiry, tenant isolation, single billing authority, late active event
after cancellation, customer mismatch, read failure, duplicate audit, owner
pause/settings retention, admission retention and two concurrent reconciliations.
Actual isolated backup/restore confirms access is not revived from an archive.
Controlled HTTP tests cover both clients' request/authentication contracts,
signature/mode/object failures, redirects, throttling and provider errors.

Remaining: persist the reviewed customer/plan catalog configuration and wire a
bounded operator ingress/worker with periodic refresh; authenticated customer/
checkout setup and consent; provider sandbox end-to-end cancellation/refund/
out-of-order acceptance. Refunded invoice/payment reconciliation and commercial
renewal/tax policy are not yet implemented. No provider credentials were used,

## 2026-10-17 — refund and dispute entitlement policy

The user approved pausing access for a confirmed dispute or full refund. Partial
refunds preserve access only when the fresh provider read still reports active,
paid subscription state. A later provider refresh can restore access only after
that same authoritative active/paid check; the signed event snapshot itself never
grants access. The reconciler records the normalized billing action in its audit
row.

Stripe `charge.refunded` distinguishes full and partial amounts and routes a
customer-only event only when the configured provider customer maps to exactly
one workspace. Razorpay refund callbacks use the signed payment/refund amounts
and the same unique-customer binding. Ambiguous or unknown mappings fail closed.
Tests cover signature classification, unique customer routing, ambiguity
rejection, full-refund/dispute pause, partial-refund preservation, and restoration
after a fresh paid/active read.

## 2026-10-17 — durable charge/payment reference resolution

Migration 0051 and `billing/references.py` persist verified charge/payment-only
callbacks before any provider I/O. Stripe charge lookup and Razorpay payment
lookup use fixed HTTPS GET endpoints, explicit account/key-mode configuration,
bounded bodies/deadlines, no redirects/proxies/retries, and return only routing
IDs. Raw payment contents are discarded. Razorpay dispute created/under-review/
action-required/won/lost/closed callbacks now normalize into the existing policy.
Refund callbacks without a customer ID also enter this queue using the signed
payment ID; full/partial classification uses cumulative signed payment amounts,
and a supplied refund entity must match the same processed payment.

The worker consumes a committed attempt before lookup, holds a session advisory
lock through the operation, and resolves only one matching configured workspace
in the same provider/account scope. Unknown and ambiguous mappings cannot enqueue
subscription work. Failed reads back off and quarantine after five attempts;
worker loss retains the attempt. Resolution and inbox insertion are atomic and
idempotent. The worker's ten-action budget includes both reference lookups and
subscription reconciliation. No access is granted by reference resolution.

Verified locally: signed HTTP ingress → persisted reference → controlled provider
GET → subscription inbox → PostgreSQL entitlement policy for both providers;
duplicate/conflicting events; ambiguous customer and cross-account rejection;
application-role denial; backoff/quarantine; held-lock duplicate prevention; and
simulated worker loss after attempt commit. No live provider request was made.
