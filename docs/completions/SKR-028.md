# SKR-028 — Isolated backend execution

**Implementation ready for integration; actual Docker filesystem/network
isolation remains unverified because image builds hit Docker storage I/O.**

`src/skriller/security/runner.py` directly reuses copied Agent-Reach
`make_private_dir`, `utf8_subprocess_env`, `scrub_url_credentials` and URL/host
validation. The nonempty explicit environment allowlist prevents the reused
UTF-8 helper's fallback to `os.environ`; no host tokens or credential settings
are passed to the backend. No vendor/reference algorithms were rewritten.

`IsolatedRunner.run(operation, target)` currently exposes the reviewed
`youtube_metadata` read operation. It builds fixed yt-dlp arguments with
`--ignore-config`, no downloads/playlists, timeout and a literal `--` delimiter.
Unknown/write/shell operations are rejected; new platform commands require
explicit reviewed adapter additions rather than accepting model-supplied argv.

The worker must be an administrator-reviewed digest-pinned image with the
installed frozen product runtime. The supplied worker base is an isolation
fixture and deliberately does not claim an installed yt-dlp/browser runtime.
Docker gets only a per-task private workspace mount, read-only root filesystem,
bounded tmpfs/PIDs/memory/CPU and the guarded internal network. The worker
entrypoint applies firewall rules and drops all capabilities before executing
as an unprivileged UID. Host home, credential directories, Docker socket and
other task workspaces are never mounted. This filesystem boundary comes from
the container; changing HOME/cwd alone is not asserted to provide isolation.

The process primitive drains stdout/stderr concurrently, bounds combined bytes,
enforces a deadline and kills the process group including grandchildren.
`RunResult` distinguishes completed/failed/timeout/output-limit/unavailable.
It also reports `cleanup_failed` if Docker cannot confirm removal; successful
backend output never hides failure to release the isolated worker.
The orchestration runner explicitly removes its uniquely named Docker container
in `finally` because killing the Docker client alone does not stop daemon-owned
containers. Runtime source credentials, when added later, require explicit
tenant-owned mounts from SKR-029 rather than automatic discovery.

## Verification

Real subprocess tests verify child-process timeout termination, stdout/stderr
flood termination, UTF-8 handling and URL-secret redaction. Command tests verify
shell syntax remains a literal URL argument and rejects unsupported operations.
Runner construction tests verify immutable-image/guarded-network requirements,
minimal environment, task-only mount and removal of the exact task container.
Combined URL/proxy/runner suite initially passed **24 tests**; additional
unavailable-executable and opt-in container tests are recorded in the final
suite run below.

Final combined rerun before cleanup-result hardening: **25 passed, 1 explicit
container gate skipped**. Final runner-only rerun after hardening: **8 passed**;
effective combined coverage is 26 passing tests. Ruff check/format and unchanged
Agent-Reach provenance pass.

The kernel/filesystem gate in `tests/security/test_container_boundary.py` is
explicitly opt-in. Both attempted Docker image builds failed with Docker Desktop
`metadata_v2.db: input/output error`; therefore actual worker firewall, host-file
isolation and installed backend execution have **not** passed verification.
This is a release dependency; there is no unsandboxed fallback.

The controller needs trusted Docker access; never expose its Docker socket to
workers. Restore Docker storage, build/publish the reviewed runtime image,
pin its digest, start `infra/egress/compose.yaml`, and run the opt-in boundary
test before deploying backend operations. Linux firewall/container code is not
a native macOS sandbox implementation.
