# SKR-040 — bounded native proxy routes and sticky continuity

Implemented and verified locally on 2026-10-15. Hosted/isolation acceptance remains pending as described below; this is not a claim that every connector or provider now supports rotation.

## Implemented boundary

`connectors/proxies.py` uses the copied Scrapling `ProxyRotator`, `cyclic_rotation` and `is_proxy_error`; it does not replace fetch or scraper algorithms. Provider configuration is a distinct tenant-private `proxy` connection, stored in the existing authenticated-encryption envelope. Searchable `Source` values and account-reader runner bindings remain separate. Connection create/list/reconnect/revoke DTOs accept the separate connection source, with regenerated OpenAPI/client types.

A configuration uses `auth_kind=api_key` and one encrypted `payload.credentials.api_key` JSON string with exactly these fields:

```json
{
  "providers": [{"server": "https://provider.example", "username": "provider-sticky-task-session", "password": "configured-provider-secret"}],
  "usd_per_gb": "4",
  "max_attempts": 3,
  "max_bytes": 10485760
}
```

Only standard HTTP/HTTPS provider ports (80/443), up to eight endpoints, three transport attempts and ten MiB per task/source route are supported. The configured username must express the provider's own sticky-session convention. The application preserves credentials and endpoint selection; it cannot attest a provider's internal session semantics. No provider purchase, source-account read or live provider verification was performed.

The durable migration `0025` adds tenant-scoped task/source route bindings, attempts, failure and sent/received traffic counters. Both provider and account connection references are bound. Revocation, replacement, configuration changes and account-reference changes cannot silently rebind a route. Authenticated tasks fail closed after a failed route; public tasks may advance the copied cyclic rotation on a subsequent explicitly budgeted call. Transport code performs no internal retry or direct fallback.

`HTTPFetcher` automatically uses exactly one active tenant proxy-purpose connection for the supported native loopback gateway path. Existing bindings take precedence over newly configured credentials. No configured provider persists an explicit direct binding and preserves the existing guarded public route; adding a provider between pages does not change the route of that task. RSS shares this HTTP boundary. Native per-operation gateways use a server-generated opaque credential, stripped before forwarding. Workspace/job/source headers supplied by HTTP clients never choose a route.

`task_route` validates actor, workspace, job, plan revision, approved source, account/proxy availability, source switch, job control and deadline. It reserves maximum configured traffic cost before dialing, keeps failure exposure as estimated usage, and reconciles successful locally measured traffic without double-counting the enclosing adapter's fetch-attempt reservation. The existing HTTP adapter still owns source capacity/cadence, decoded body limits, per-URL attempts, redirects and cancellation. Concurrent route use is refused while a traffic reservation is held; an interrupted/unreconciled call remains conservatively held.

The mandatory `GuardedProxy` validates public destination DNS/numeric addresses before provider dispatch. Provider CONNECT targets the vetted numeric IP; the destination Host/SNI remains the source host. Provider endpoint DNS is also vetted and pinned, with normal TLS certificate verification for HTTPS providers. Provider credentials occur only in the upstream CONNECT handshake. Source requests never receive proxy credentials. Traffic and deadline checks also occur during relay. Async gateway startup/cleanup are tracked and shielded so task cancellation does not abandon the owned gateway.

Traffic counters represent tunneled bytes sent and received, including destination TLS bytes when applicable, excluding the upstream provider CONNECT handshake. Success cost reconciliation uses the configured tariff and these local counters; it is not confirmation of a provider invoice. Unavailable/failed transport retains its reserved maximum estimate.

## Remaining acceptance gate

The isolated Docker browser has an immutable fixed gateway/firewall route. It cannot reach an ephemeral native loopback gateway. A server-authenticated task control plane on that isolated gateway is still required before configured providers can be used by dynamic/stealth browser execution or hosted HTTP workers. Configured browser provider execution is refused before reservation/dispatch, preventing a static-to-browser route change. Configured provider use through a non-loopback `egress-proxy` endpoint also fails closed. Existing unconfigured browser/public routes continue unchanged.

GitHub native metadata transport now shares the task provider route (see the verification below). Account-backed LinkedIn/Reddit and hosted deployment remain deferred. Therefore the ticket's broad cross-adapter/isolated-runtime acceptance should remain pending even though the supported native HTTP/RSS path and trusted sticky gateway plane are implemented and reviewable.


## GitHub native task routing — 2026-10-15

The default GitHub collection path now enters the same cancellation-safe `HTTPFetcher.proxy_for` gateway lifetime used by HTTP/RSS, then gives the selected endpoint to the existing bounded public GitHub client. It binds the persisted tenant/job/source choice and attempt UUID. Only the gateway's opaque 43-character task credential is accepted on an authenticated loopback proxy URL; ordinary proxy credentials and remote authenticated gateways are rejected. HTTPX retains certificate verification, fixed GitHub API operations, no environment proxies, no redirects and no source authorization. Provider credentials remain in the encrypted route controller.

Three real local HTTPS/worker/PostgreSQL cases verify a zero-cost configured provider with real authenticated gateway CONNECT and origin TLS, a failed provider with no direct fallback, and a priced provider rejected before dialing under the prompt job's zero-dollar cap. The fixture CA is trusted only by the test HTTP client; production TLS validation is unchanged. Successful traffic is measured/reconciled; failed traffic retains estimated exposure. Origin headers contain neither Authorization nor Proxy-Authorization, persisted diagnostics exclude the fixture secret, accepted public API counters retain evidence, and duplicate/provider retry behavior remains bounded. The shared gateway startup/cleanup cancellation regressions also pass.
