# SKR-021 — Transactional outbox dispatch

Implemented provisionally; required real RabbitMQ verification remains pending because Docker/broker is unavailable. Actual PostgreSQL plus actual Celery/Kombu memory transport integration passed **8 tests**; memory transport is explicitly not durable RabbitMQ proof. Do not mark this ticket done until the RabbitMQ gate passes.

`skriller.jobs.outbox.submit` validates the persisted immutable SearchPlan contract, matching workspace/conversation/revision, and inserts the logical job, queued-state event, and ID-only outbox in the caller's single tenant transaction. Bounded request idempotency keys return the same job/outbox under concurrent submissions. Rolled-back submissions leave neither row. Terminal duplicate submissions do not restart a job.

`OutboxDispatcher` publishes one row per transaction with PostgreSQL FOR UPDATE SKIP LOCKED, retaining the row until publisher confirmation, then records published_at. A committed unpublished row recovers on a later dispatcher run. Publication exceptions leave it pending. A crash after confirmation but before commit replays the same stable outbox/message ID; delivery is at least once and SKR-022 must deduplicate checkpoint effects. Dispatcher operates through restricted tenant sessions with trusted DispatchScope identities, not owner/superuser cross-tenant queries.

`CeleryPublisher` uses the genuine Celery task protocol, durable persistent delivery, bounded connection/write timeout, disabled unbounded publish retry, RabbitMQ publisher confirms, and the `skriller.jobs` queue. AMQP/AMQPS are supported; memory transport requires explicit test opt-in. Only opaque workspace/job/actor/optional attempt IDs enter task args. Topic names are allowlisted. Tasks are named `skriller.jobs.execute_job`, `skriller.jobs.execute_attempt`, and `skriller.jobs.cancel_job`; worker handlers are SKR-022. This module does not yet wire API run routes or a scheduler process; those integration boundaries are downstream work.

Passed tests: concurrent same-request submissions produce one job/outbox/event; precommit rollback leaves no job/outbox; postcommit dispatcher recovery publishes; after-publish simulated process crash leaves pending/replays same ID; concurrent dispatchers skip the locked row and publish once; invalid/wrong-scope immutable plans cannot submit; ID-only/task/message properties pass actual Celery/Kombu protocol checks; memory test opt-in and invalid payload/topic checks. Ruff and mypy pass. These checks establish database recovery/protocol behavior, not RabbitMQ persistence, restart, or publisher-confirm behavior.

The required remaining gate is a genuine RabbitMQ connection/persistent queue, crash/restart recovery, and confirmed publication under the same dispatcher interface. No external credentials or unrelated databases were used.
