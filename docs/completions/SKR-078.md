# SKR-078 local recovery and accounting acceptance

Status: **implemented_pending_verification**.

Fixed a post-provider persistence failure: the previous atomic result/usage transaction could roll back a known successful call's usage when the result writer raised. The worker now rolls back tentative results, then retains confirmed actual usage in a separate scoped transaction, marks the attempt failed, pauses the job, emits redacted failure/zero-result stage observations, and prevents automatic redelivery. Malformed accounting retains the full estimated ceiling instead of treating the call as free. If the original transaction committed but its acknowledgment was lost, its matching generation/owner checkpoint is returned without another provider call or charge. A late failure does not alter a newer attempt's ownership.

The new fault-injection suite uses real PostgreSQL to cover writer exceptions, SQL transaction failure, cross-tenant result references, malformed accounting, duplicate delivery while I/O runs, and cancellation before a late reply. It also kills an owned Python child during an open result transaction, proves rollback, expires only the synthetic attempt's lease, and recovers one logical checkpoint. The interrupted call retains an estimated charge and the replacement call a separate confirmed charge; the unknown reply is not presented as recovered evidence. A commit-acknowledgment fault returns the already-committed checkpoint once. Existing actual RabbitMQ redelivery and kill-after-checkpoint-before-ack tests passed in the initial group.

`resume_readiness` now shares the exact preflight used by resume. Results expose advisory `resume_status`: `available`, `new_prompt_required`, `deadline_expired`, `requires_reconciliation`, `budget_exhausted`, or `not_paused`. The mutation repeats checks under the job lock; the advisory never authorizes execution. Checkpoint failures preserve useful prior results, include a safe explanation, and return `requires_reconciliation`; resume still returns 409. The Luna frontend update validates this optional status, preserves compatibility with older payloads, displays reason-specific recovery guidance, and exposes Resume only for an explicit `available` response. A missing status is treated as unknown and cannot authorize the action.
