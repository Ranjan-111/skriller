# SKR-014 — Tenant isolation

Implemented owner-run Alembic migrations, explicitly provisioned `skriller_app` restricted login role, workspaces/memberships, owner/member checks, and transaction-local actor/workspace contexts. The application role is neither table owner nor superuser and cannot bypass RLS, create databases/roles, or inherit other roles. Normal application sessions reject owner/privileged connections.

RLS independently checks both requested workspace and actor membership; changing only the workspace context does not grant access. Membership mutation and workspace mutation require ownership. Workspace creation uses a narrowly scoped security-definer function with fixed search path; maintenance uses separate owner credentials. SQL credentials are parameterized/quoted and not logged.

Four tests passed against local PostgreSQL 18: cross-tenant rejection at repository/session and direct-SQL boundary, same pooled backend context cleanup after commit and rollback, member rejection for adding owners even via direct SQL, and rejection of privileged owner connections for application operations. Initial sandbox run could not connect to loopback; approved local integration execution succeeded. No SQLite fallback or external platform call.

Actor identity must come from server-verified Firebase identity; these database contexts are not client input authorization. Backend application credentials are trusted, and database RLS protects tenant-scoped queries from accidental omission rather than a compromised application server forging actor identity.
