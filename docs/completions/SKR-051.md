# SKR-051 — professional contacts and dated role freshness

Implemented the scoped contact/freshness component in `qualification/contacts.py`, with append-only role-history migration 0015. It does not perform SMTP, guessing, external DNS or live account access.

Contact syntax, MX-domain status, professional ownership and mailbox status remain separate. MX presence cannot verify an address or identity. Address exposure requires the exact original entity's accepted observed `work_email` or `professional_email` claim, linked current evidence containing the whole value and a valid public HTTP(S) source URL. Generic email, inferred/unverified claims, missing quotes, expired evidence and another person's claims do not become usable contacts. Supplied MX metadata is a trusted connector observation seam; no live DNS verification is claimed.

Role refresh requires accepted observed role and `role_effective_date` claims with the same original entity and evidence. Both source dates must be literal ISO values in the evidence, not future dates; the replacement must be strictly later and actually changed. Existing unresolved conflicts remain conflicts: no automated acceptance occurs. Tests explicitly simulate trusted review before refreshing, because normal repository insertion marks differing values conflicting. Product review orchestration remains a dependency.

Both original claims are retained. The append-only dated supersession record supports `historical`, `current` and `unknown` projections with the original claim/entity IDs. Validated current role dates supply `event_at`; collection timestamps never substitute for role dates. Conflicts, malformed JSON, future/equal dates, expired evidence and another person's role leave current status unknown. No reviewed identity-group link transfers contact ownership or employment chronology between original records.
