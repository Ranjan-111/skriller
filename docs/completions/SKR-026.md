# SKR-026 — persisted progress transport

Implemented authorised workspace-scoped job snapshots and SSE event streams in `src/skriller/progress.py`. Snapshot fields and event envelopes are actual OpenAPI DTOs. Clients use generated types and send Bearer identity and Last-Event-ID in headers. No query credentials are accepted. Local documented Uvicorn startup disables request access logging to avoid recording unsolicited credential query values.

Events are ordered by persisted cursor, streamed in bounded batches of100, and replay strictly after Last-Event-ID. Running streams emit heartbeats, stop on disconnect, and recheck membership on every poll. Terminal streams drain all persisted batches before closing. Snapshot contains persisted state/stage/version/reason; transport invents no counts, qualifications or results. Authentication is the existing Firebase verifier boundary, tested here through explicit dependency overrides; real Firebase configuration remains SKR-013's open gate.

Actual verification2026-10-12: four real PostgreSQL18.4/API transport tests pass, covering complete replay, reconnect after intermediate/final cursor, draining more than100events, actual state snapshot, invalid cursor, token-query rejection, missing authentication, nonmember and cross-workspace job rejection. Frontend32tests pass including generated-type SSE decoding, fragmented frames, exact large-ID headers, malformed envelopes, bounded memory and cancellation cleanup. Root mypyAPI/progress/contracts passes; Ruff passes for ownedfiles.

Every event allocation now locks its tenant-bound job row before allocating the persisted sequence. The real concurrency regression holds the first transaction open and verifies the second cannot allocate/commit a later cursor first; after release both events replay in order. Automatic progress UI/reconnect presentation remains later product UX work. The transport polling interval is1second; deployment proxy must retain no-buffer/no-cache headers.
